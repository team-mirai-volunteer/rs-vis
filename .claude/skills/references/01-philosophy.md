# 01. デザイン哲学 — チームみらいらしさをコードに移すための前提

このドキュメントは「なぜ `#2AA693` なのか」「なぜ `<button>` ではなく `Button` なのか」「なぜ AI 出力に必ずラベルを付けるのか」の **根拠** を残すためのもの。トークンや禁止ルールの暗記だけでは伝わらない、デザイナー(山根さん)と開発本部が共有している判断軸を言語化した。

トークン値・コンポーネント仕様だけが欲しい場合は [`02-tokens.md`](02-tokens.md) や [`03-components.md`](03-components.md) を見るほうが速い。**ここは「揺らいだときに戻ってくる場所」**。

## 大前提：3 つの軸

チームみらいの UI 判断は次の 3 つの軸の優先順で決まる。

```
1. 親切さ(A11y / 色覚配慮 / 軽量 / 文字組み)
2. 統一感(複数プロダクト・複数画面でブレない)
3. 美しさ(装飾・遊び・流行)
```

3 つは独立ではない。**`1` を満たさない美しさは採用しない**。具体例:

- 「白背景に薄グレーのキャプション」が一見おしゃれでも、コントラスト比 4.5:1 を切るなら採用しない(`text-mirai-text-muted` を 12px 以下の本文に使うのを禁止しているのはこのため)
- 「派手な hero グラデーション」が映えても、`bg-mirai-gradient` は 1 画面 1 つだけに留める(ノイズになる)
- 「アニメーション multi-easing で華やか」も `transition: all` を禁止する(パフォーマンス・予測可能性の代償が大きい)

### なぜ親切さが最優先か

チームみらいは政治団体であり、Web プロダクトの読者には ICT リテラシーや視認能力のばらつきが大きい。「美しいが読めない」「速いが視覚障害者に届かない」UI はミッションそのものに反する。広報ガイドラインの「分断を煽らない」([`brand-guidelines.md`](../../../05-communications/brand-guidelines.md))と整合する判断。

## デザイン原則 7 つ

### 原則 1：色は感覚で選ばない、トークンで選ぶ

> 色を『青っぽく』と書くと AI slop が出る、`#0A0A0A` と書くと出ない(StyleSeed / Mindstudio)

これは AI コーディングエージェントだけの話ではなく **人間にも当てはまる**。山根さんが Figma で「ちょっとティール寄りで」と微調整しても、エンジニアが「`#26A69A` か `#2AA693` か」を都度判断するなら統一感は瓦解する。

ルール:

- **`globals.css` の `@theme inline` に定義されたトークンしか使わない**
- 新色が必要なときは *まず* `globals.css` にトークン名と hex を足す PR を切る。実装はその後
- arbitrary value(`text-[#26A69A]`)は **発見次第 PR で弾く**

なぜ厳格にするか：色のばらつきは *単体で見ると気づかれないが、複数画面を並べると瞬時に瓦解する*。「みらい議会のヘッダー」と「まるみえのヘッダー」が並ぶ瞬間に違和感を生むレベルの差は、目視ではなくトークンの一致で防ぐ。

### 原則 2：オーバーコミットメントしない

> 「リアルタイム」「即時」のような誇張は使わない(特に「みらい まる見え政治資金」)— `brand-guidelines.md` §5

UI 文言と機能の間に齟齬が出ると、ユーザーは UI を信用しなくなる。具体的に避けたい用語:

- ❌ 「リアルタイム」→ ✅ 「最新の」「直近の」
- ❌ 「即時」→ ✅ 「数秒で」「すぐに」
- ❌ 「絶対に」「100%」→ ✅ 「現時点では」「多くの場合」
- ❌ 「AI が判断」→ ✅ 「AI による分析(参考情報)」

特に AI 出力を表示する画面では、**責任の所在をラベルに含める** のがルール。山根さんがみらい議会の「おすすめ順」を「AI おすすめ順」に変更を提案した経緯([Slack 2026-05-13](https://team-mirai-staff.slack.com/archives/C0AFPQKSKS7/p1774620746459069?thread_ts=1774620746.459069))はその好例：

> 「おすすめ順」はチームみらいがおすすめしてる意見な感じがするのでラベルを変えた方がよさそう
> 実態としては、AI が意見の情報充実度 richness を評価してその順に並べているもの
> → 「AI おすすめ順」(AI のおすすめだよと逃げる)

「逃げる」と表現しているが、これは責任の所在の明示。**信頼を作るために小さく嘘をつかない**。

### 原則 3：文字組みのクオリティに妥協しない

> figma、canva は紙の入稿には使えない(使えるが文字組みのクオリティが低いのであまり使いたくない)— 山根 [Slack 2026-04-17](https://team-mirai-staff.slack.com/archives/C0AEN3H1EF8/p1771049165674179?thread_ts=1771038693.725449)

文字組み = フォントファミリー選定・ウェイト・行間・字間・改行位置。Web では完全には制御できないが、最低限は守る:

- **フォントスタックは `Hiragino Sans` を先頭** にする。`Hiragino Kaku Gothic Std` は W3/W8 の 2 ウェイトしか持たないため、`font-weight: 400/500` が **極太** に解決されてしまう(CSS Font Matching Algorithm の挙動)。詳細は [`02-tokens.md` §2.2](02-tokens.md)。これは jujunjun110 さんが詳細調査して山根さんと共有した経緯がある([Slack 2026-04-13](https://team-mirai-staff.slack.com/archives/C0AFZQSG1GC/p1774076018849129?thread_ts=1773623258.419589))
- **`leading-relaxed`(1.875)を本文に使う**。日本語は欧文より行間を広く取った方が読みやすい
- **見出しは Bold/SemiBold のみ**。ExtraBold(800)は装飾用途以外で使わない
- **1 行 30〜40 文字程度で折り返す**。最大幅は `max-w-prose` 程度

### 原則 4：UI 統一は遷移と情報設計を含む

> デザインシステムで複数プロダクトの UI を統一することに加えて、まさにページ遷移など UX 観点も入ると最高だなという感触 — 山根 [Slack 2026-03-26](https://team-mirai-staff.slack.com/archives/C0AFZQSG1GC/p1771900905338539?thread_ts=1771688701.701659)

ボタンの色を揃えただけでは統一感は出ない。山根さんが「みらい議会」と「まるみえ政治資金」を行き来したときに自然に感じる滑らかさは、**遷移パターン** と **情報の置き場所** の一貫性から来る。具体的:

- **ナビゲーション**：トップに戻る・前画面に戻る・ヘルプを呼ぶ位置を 全プロダクトで揃える(PC は左サイドバー固定、モバイルは Sheet ドロワー)
- **「もっと見る」パターン**：長いリストは「5 件表示 → もっと見る」([guidelines.md 叩き台](https://team-mirai-staff.slack.com/archives/C0AFZQSG1GC/p1771943529805999?thread_ts=1771943515.567089))
- **空状態 → 行動可能なCTA を必ず置く**([`04-patterns.md`](04-patterns.md))
- **ステータス表示は常に色とアイコンの両方**：✅ Pass / ⚠️ Warning / ❌ Error

### 原則 5：シンプル主義、1 画面 1 主役

- **プライマリ CTA は 1 画面 1 つ**。`<Button variant="default">` のグラデピルを複数並べない(並べたいときは `outline` と組み合わせて主従をつける)
- **`bg-mirai-gradient` は 1 画面 1 箇所**。hero / 主要 CTA / 主要 badge のどこかで使うがすべてには使わない
- **`rounded-2xl` 以上は使わない**。カードは `rounded-xl`(12px)、ピル要素は `rounded-full`、入力は `rounded-md`(6px) のみ
- **影は `shadow-xs` / `shadow-sm` / `shadow-md` だけ**。`shadow-lg` 以上は装飾的すぎる
- **アニメーションは目的があるときだけ**。ローディングの `pulse`・ホバーの `opacity-90` のような *機能を伝える* アニメーションは OK。`transition: all` の万能指定はパフォーマンス低下を招くので禁止
- **「ロゴでいい」発想を持つ**。山根さんが安野議員の自己紹介ボードで「自己紹介用ですよね？ロゴでいいんじゃないかな」と即答した([Slack 2026-05-08](https://team-mirai-staff.slack.com/archives/C0AF339V3CZ/p1778659270636029?thread_ts=1778658909.711359))のはシンプル主義の表れ

### 原則 6：情報設計を尊重する

> 非公式国民 pedia 情報設計がうまい — 山根 [Slack 2026-04-20](https://team-mirai-staff.slack.com/archives/C0AN5TADWS2/p1776177714823679)

UI コンポーネントの選び方より前に、**何を最初に出して、何を後ろに回すか** の判断が大事。

- **「読むべき要素」と「クリックする要素」を視覚的に分離する**：本文 → 灰色寄り(`text-foreground` `#1F2937`)、CTA → 強い色(`bg-primary` `#2AA693`)。読んでいる最中にボタンが視野に入って煩わしくならない配色になっている
- **「責任の所在」を視覚化する**：AI 出力には専用ラベル、ユーザー投稿には投稿者名と日時、編集可能ならそれを示すアイコン
- **「リスクの大きさ」を視覚化する**：削除のような unrevocable な操作は `destructive` variant + 確認モーダル。一方、フィルタの切替のような可逆な操作はその場で即適用
- **「過去」と「現在進行中」と「未来」を区別する**：完了タスクは `text-muted-foreground` + 取り消し線、進行中は `text-foreground`、未来は `text-muted-foreground` のみ

### 原則 7：書ける人がデザインする時代に対応する

> Claude Code x デザインツール(Figma, Pencil.dev など)で、山根さんだけでなく PM やエンジニアもちみのデザインシステムベースでデザインのたたきをつくれるといいなと — k.murai [Slack 2026-03-26](https://team-mirai-staff.slack.com/archives/C0AFZQSG1GC/p1771900555197499?thread_ts=1771688701.701659)

デザインシステムの目的は「山根さんでなくても、ちみらしい UI が出てくる」状態を作ること。そのためには:

- **ルールを Markdown 1 枚で AI に渡せる**(このスキルパッケージ全体がそのため)
- **トークン名を見ただけで意味が分かる**(`--color-mirai-text-muted` のように意味タグを含む)
- **「○○禁止」を grep でチェックできる**([`08-antipatterns.md`](08-antipatterns.md))
- **逸脱が必要なときは PR コメントで議論する**(暗黙の例外を作らない)

## アンチパターンと、その背景にある反省

これらは「過去に実際に発生した／発生しそうな失敗」とその学び。

### 「Figma スクショから色を推測する」

→ 結果：見た目同じだが hex が `#26A693` vs `#2AA693` で 1 ピクセル違う。複数画面を並べると違和感を生む。**`get_variable_defs` を呼んで実値を取る**。`mirai-gikai/AGENTS.md` に明文化されている。

### 「`Hiragino Kaku Gothic Std` 単体でフォント指定」

→ 結果：`font-weight: 400` が ExtraBold(800)に解決される現象が発生。Figma Make が初期に書き出していたコードで実際に起きた。**`Hiragino Sans` を先頭にした 4 段スタックを使う**。

### 「`rounded-xl` を一般要素に使う」

→ 結果：Figma Make の旧設定で `rounded-xl` が `--radius-button: 40px`(ピル相当)にマッピングされている。書き出しコードをそのままコミットすると見た目がかなり丸くなる。**一般要素は `rounded-md`(6px) を使う**。詳細は [`02-tokens.md` §2.3](02-tokens.md)

### 「`<button>` を直書きしたあと cva variants が欲しくなる」

→ 結果：プロジェクトに `<button>` と `<Button>` が混在し、ホバー挙動・focus ring・disabled スタイルがバラつく。**最初から `<Button>` を使う**。`mirai-gikai/AGENTS.md` で明文化済み。

### 「`text-2xl font-bold leading-none` を見出しに当てる」

→ 結果：別の画面では `text-2xl font-semibold leading-tight` を使っていて、視覚的に同じ「見出し」なのにスタイルがバラつく。**タイポは globals.css 側で一元管理する** か、**`text-2xl` と `font-bold` のように 1 役 1 クラスを固定する**。

### 「巨大配列を `map()` で生 DOM 化」

→ 結果：法案検討ツールのコメント表示で 70 件を超えた時点でブラウザが重くなった事例がある([山根 2026-04-19](https://team-mirai-staff.slack.com/archives/C0AFPQKSKS7/p1774620746459069?thread_ts=1774620746.459069))。**100 件以上見込むリストは virtualize する**。

## このスキルが守ろうとしている契約

このパッケージは「山根さんが個別判断で当てている直感」を、デザイナーが現場にいなくても再現できる状態にするためのもの。**完全には再現できない**：細部の判断(例：「特定文脈で `rounded-xl` を使うか `rounded-2xl` を使うか」「グラデーションの向きを `to bottom right` から `to bottom left` に変えるか」)は、最終的に山根さんとの会話に戻る。

ただし、**「明文化されていれば 80% は再現できる」** ことを目指している。再現できなかった 20% は PR レビューで議論し、必要なら本ドキュメントを更新する。
