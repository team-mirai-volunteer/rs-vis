# 概算要求の自動取得・検索

## 対象と位置付け

`/budget-requests` は、財務省の年度索引に掲載された各府省・機関等の公開先から、概算要求資料を機械収集する独立ビューです。初期対象は2027年度（令和9年度）。行政事業レビューの「翌年度要求」を当年度データに読み替える仕組みではありません。成立予算・執行額・AI評価とも分離しています。

起点は [財務省2027年度索引](https://www.mof.go.jp/policy/budget/budger_workflow/budget/fy2027/index.html) です。概要・一般会計・特別会計の3つのリンク表のURLをHTMLから発見し、そこに実際に掲載された府省のURLをたどります。府省別のファイルURLを連番推測で生成しません。特別会計の行名は所管名と取り違えず、一般会計等の掲載先URLとの一致で所管を対応させます。空セルや読めない公開先から資料URLを捏造しません。

## 実行

```sh
npm ci
npm run fetch:budget-requests
npm run validate:budget-requests
# 保存済み原本だけで新しい抽出器を再適用（ネット接続なし）
npm run reprocess:budget-requests
npm run test:budget-requests
```

Node.js 22と既存のnpm依存だけで動きます。PDFは既存`pdf-parse`依存の`pdfjs-dist`と同梱CMapで読みます。Poppler・外部LLM・OCRサービス・新しいAPIキーは不要です。

```sh
# 小さい実取得確認。上限外は未取得として残る
node --import tsx scripts/fetch-budget-requests.ts --year 2027 --max-files 160 --max-pages 120 --concurrency 4
# 中断再開。未完了の取得サイクルを日付をまたいで再開し、原本の取得日時を保持
node --import tsx scripts/fetch-budget-requests.ts --year 2027 --resume
```

CLIの既定はHTML200件、資料2,000件、掲載先から3階層、並列3です。手動起動のActionsは小さいバッチで進め、中断時は保存済みの原本と進捗を再利用します。上限に達した資料はカタログに残ります。未処理の理由・件数は運用レポートに記録し、単なる処理順・上限では公開スナップショットを更新しません。過年度の明示されたリンク、他府省への参照リンク、税制・機構定員の別系統資料、歳入資料は歳出要求額に混ぜません。政府ドメイン以外とWARPのリンク・リダイレクトは取得しません。URLの明示的な年度（fy2027、gaisan/r9等）が対象年度と矛盾する資料は、リンクラベルが当年度でも取り込みません。過去データの再利用・オフライン再抽出にも同じ検査を適用します。1件40MB、HTTPタイムアウト30秒、再試行1回に制限します。1件の失敗で他の資料を止めません。

年度判定は親見出しと年別セクションを引き継ぎます。例えば「令和8年度」の下に「非公共事業」があっても年度を失いません。段落・リスト項目の `【令和9年度予算】` のような区切りも扱います。一方、公開年度の見出しの下に翌年度要求がある場合は、明示されたリンク自身の要求年度を優先します。MEXTの`r01`、環境省の`r06`のようなCMS用ディレクトリや、デジタル庁の公開年度を含むファイル名を一律に要求年度とはみなしません。年度のない各局予算ページは入口としてたどり、リンク先の年度別セクションで対象を絞ります。

HTMLコメント、フッター、サイドバー等を資料リンクとして数えません。保存済みHTMLで、以前収集したリンクが明示的に対象外と確認できる場合は、関連する過年度・無関係なカタログ項目も除外します。原本は削除しません。単にリンクが見つからない場合、掲載ページが読めない場合、または別の当年度ページから確認できる場合は消失と断定しません。財務省が当年度索引に掲載する入口は、別ページのフッターにも出ることを理由に除外しません。

## 保存・改訂・障害

- 公開データ: `public/data/budget-requests-2027.json.gz`。JSON本体はGit管理せず、既存サーバー用データローダーが圧縮データを読む
- 原本: `data/budget-requests/sources/{SHA-256}`。Git管理しない
- 資料ごとに元URL、親の掲載URL、原本の取得日時、スナップショット記録時の最終試行、SHA-256、改訂番号、過去のハッシュと取得日時を保持
- 同一URLで内容が変わった場合は改訂番号を増やして再抽出。同じバイト列の再取得では改訂番号を増やさない
- 原本ハッシュ・レコード・状態等に実質的な変更がなければ、生成日時・資料/行の取得日時を含めて前回スナップショットを維持し、圧縮ファイルも同一になる。無変更の確認時刻は公開データを書き換えず運用レポートに保存。画面も「内容・状態の更新」「記録時の最終試行」と表示し、再確認時刻と取り違えない
- 実行限定の注記は実行ごとに更新し、警告を重複追加しない。前回データのオブジェクト・配列は変更しない
- 取得に失敗した場合は、前回成功時の行とハッシュを保持し、「今回の取得失敗・過去時点の値」と表示
- 新しいバイト列の抽出に失敗した場合は、古い行を新しい資料の値として保持しない
- 索引・掲載ページが取得できない場合も、前回の資料を消さず、再発見・再確認できていない旨を表示
- 府省の掲載ページだけが取得失敗した場合、ハッシュ検証済みの保存HTMLがあれば当年度リンクの探索を続行する。掲載ページの状態は取得失敗のまま、以前の取得日時と今回のエラーを保持
- ファイル更新は一時ファイルからのatomic rename。各バッチ後に保存し、中断時も最後のバッチを復旧可能

`discovered / fetched / extracted / partial / unsupported / fetch_failed / extraction_failed` を分離します。「取得成功歴」には過去成功を、「抽出行のある資料」には一部抽出を含むことを画面に明記しています。全府省の全資料取得や総額の網羅率を示す値ではありません。

## 抽出と金額

構造化CSV/TSV（UTF-8/Shift-JIS）と既存MOF `clm` XMLを先に処理し、PDFでは「歳出概算要求額明細表」の標準列を座標で切り出します。数字の出現順だけで金額を組み立てません。標準表の通常要求額を、掲載ページの要望・投資枠へのリンクラベルだけで別枠に移し替えません。

要求年度、府省、部局、会計・勘定、科目コード、要求番号、項目名、要求・要望・特別投資枠、前年比較基準、原単位、親子関係、集計階層を保持します。公表年度・RSシート年度等を確認できない場合はnullのままです。

- 数値は1円単位のsafe integer。明示された単位がなければ数値確定しない
- `numeric`、`事項要求`、`blank`、`extraction_failed` を区別。空欄や取得失敗は0円ではない
- 各行にPDFページまたはセル、原文抜粋、原本ハッシュ、抽出方法、検証警告を保持
- PDFの分割された科目コードは隣接文字をまとめ、実原本にある中央1・3・4桁のコードと1桁の勘定見出しを扱う。金額も連続文字を丸ごと扱い、列境界で一部の桁だけを数値にしない
- CSVの「対前年度増減額」「比較増減」等を前年度額と取り違えない
- 年度、桁・小数と円単位への換算、親子の小計を検査。不一致はその行に警告を残し、原文値を勝手に補正・按分しない
- 親子・概要・通常要求・要望・投資枠には重複がある。ビュー/APIでは資料横断の金額合計を作らない
- RS対応のフィールドは `exact / inferred / unmatched`。初期実装は自動紐付けを行わず全件unmatched。未対応や新規要求も一覧に残る。古いAIスコアを引き継がない

### 確認例

[内閣府・政府広報室の標準明細](https://www.cao.go.jp/yosan/soshiki/r09/pdf/12.pdf) の通常概算要求は7,884,742千円（78.84742億円）です。[概要](https://www.cao.go.jp/yosan/soshiki/r09/gaiyou_r09.pdf) の280.49億円と同一の金額区分として扱いません。内閣官房の報道上の72.3億円も別の組織・資料で、この明細やRS国際広報事業の額に流用しません。

実原本による回帰は内閣府3ページ、財務省152ページ、文科省410ページで実施。標準表以外の総表・概要等は、一部抽出または未対応と明示します。Excel・ZIP内包表・画像PDF・自由レイアウトの要望/投資一覧・複雑な概要図は現段階では数値抽出に対応しません。リンクと未対応状態は保持します。全ての資料形式を読めるという実装ではありません。

## 無人更新

`.github/workflows/budget-requests.yml` は手動起動（workflow_dispatch）だけです。概算要求は8月末に出揃い、その後は正誤表程度しか動かないため、定期実行はしません。提出後や差し替えが分かったときに Actions の「Run workflow」から起動し、未完了のチェックポイントが残れば再度起動して続行します（定期実行が必要になったら `schedule:` を戻す。続行判定の `plan-budget-request-run.ts` はそのまま使えます）。1回100ファイル・40ページ、取得処理55分を上限とし、初回バックログも自動で順次処理します。mainへの直接pushはせず、取得・検証を通過した生成データ1ファイルだけを専用ブランチの下書き更新PRにします。自動マージは行いません。内容が変わらない取得ではコミットもPRも増やしません。

原本・再開チェックポイントをActions cacheに保存し、7日間未使用によるキャッシュ削除時は30日保持の同ワークフローの原本artifactから復元します。日付をまたぐ実行も未完了の取得サイクルを続行します。完了済みの資料の抽出で毎回上限を使い切らず、未処理の資料へ進めます。途中の原本・スナップショット・運用レポートもActions artifactに残します。キャッシュの保持制限は[GitHubの公式ドキュメント](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)を参照。ネットワークとブランチ更新の再試行は有限とし、競合した変更を強制上書きしません。

同じリポジトリのGITHUB_TOKENによるPR更新は通常のpull_requestワークフローを起動しないため、更新ワークフロー自体で型検査・テスト・データ検証を実行してから公開します。公開後は `gh workflow run checks.yml --ref automation/official-budget-requests` で通常のチェック（validate・browser・security）を更新ブランチの同じcommitに対して起動します（workflow_dispatchはGITHUB_TOKENからも起動できる例外）。起動に失敗した場合は警告を出し、手動起動が必要です。必要なブランチ保護チェックの代わりになることは保証しません。GitHub側のPR作成許可やブランチ保護が拒否する場合はジョブ失敗とし、PAT作成や保護設定の変更は行いません。

このPRを作成しただけでは定期実行を開始せず、マージ・本番デプロイも行いません。レビュー後にmainへ取り込まれたときにスケジュールが有効になります。データ更新PRも別途マージされるまで本番mainを更新しません。新しいサービス・秘密鍵・外部LLMは使用しません。

要求年度は2027に固定し、CLIは他年度も指定できます。次年度への自動切替や過去年度の公開UIは対象外です。
