## 現状の構成と問題

デスクトップ幅の右上クラスタ（`app/sankey-svg/page.tsx` L4807〜4934 + offsetControlsBlock L3094〜3184）:

```
[表示範囲カード                          ] [履歴*] [⋮] [2025年度▼] [≡]
  行1: 事業▼ Top 1〜50 ▬▬●▬ /5794件 ‹ › |←
  行2: 事業 ▬●▬ 50 ↕  支出先 ▬●▬ 50 ↕     （下に折りたたみタブ）
```
*履歴は feature flag、公開では非表示

### 問題点

1. **視覚言語が3種類混在**: 表示範囲カード（密なグリッド、border #e0e0e0、角丸6px、32px級の行）
   / ⋮ボタン（32px・影なし・半透明白）/ 年度・≡（36px・rounded-lg・shadow-md）。
   高さも 32px と 36px が並び、揃っていない。→「ガチャガチャ」の主因。
2. **設定の置き場が2つ**: 常時露出の表示範囲カードと、⋮ の表示設定ダイアログ。
   どちらに何があるかの規則が「よく使う=露出」だが、初見では区別がつかない。
3. **同じコントロールの三重定義**: TopNスライダーは (a) デスクトップのカード内
   (b) スマホの⋮ダイアログ内 (c) topNSlidersFragment として共有、オフセット行は
   デスクトップ=右上 / スマホ=左下、年度は デスクトップ=右上 / スマホ=⋮内、と
   ブレークポイントごとに配置が分岐し、5000行のページ内に条件分岐が散っている。
4. **情報過多**: 「Top 1〜50 /5794件」の状態表示・スライダー・ページング・リセットが
   全部ヘッダーに常駐。閲覧が主目的の一般ユーザーには操作より状態が分かれば足りる。

## 提案

### 方針A: 露出を「状態表示」に圧縮し、操作はポップオーバーへ（推奨・小〜中規模）

```
[検索…]                    [1〜50 / 5794件 ▾] [‹][›] [⋮] [2025年度▼] [≡]
                              └ クリックで表示範囲パネル（対象コンボ・スライダー・TopN）を開く
```

- 表示範囲カードを **「1〜50 / 5794件 ▾」ボタン1つ**に畳む。ボタン自体が現在の
  範囲表示を兼ねる（YearSelect と同じ h-9・rounded-lg・shadow-md の見た目に統一）。
- よく使う ‹ ›（前後ページング）だけ独立ボタンで残す。|←リセットはパネル内へ。
- TopNスライダー・対象コンボ・開始位置入力はパネル内に移動。
  スマホの⋮ダイアログ内 TopN と実体を共通化（topNSlidersFragment を単一の
  `RangeControlPanel` に吸収）。
- 全ボタンを 36px 高・同じ border/shadow トークンに統一。⋮ も同スタイルに。

効果: 右上の常駐要素が5グループ→4ボタン+1状態ボタンになり、視覚ノイズが大幅減。
機能は全て残る（1クリック奥に移動）。

### 方針B: SankeyToolbar コンポーネントへの構造リファクタ（大規模・保守性目的）

方針Aの見た目統一に加えて:

- `client/components/SankeySvg/SankeyToolbar.tsx` を新設し、右上クラスタ・
  スマホ配置・⋮ダイアログの内容物を **1つの宣言的なコントロール定義**
  （id / ラベル / レンダラ / 配置優先度）から生成する。
- ブレークポイントごとの「どこに出すか」はコントロール定義の
  `placement: { desktop: 'toolbar' | 'panel', compact: 'settings' | 'bottom' }`
  で表現し、page.tsx 側の isCompactWidth 分岐の散在をなくす。
- page.tsx から約400行をコンポーネントへ抽出（レイヤー規約: UIは client/components/）。

効果: 今後コントロールを増減するときの変更点が1箇所になる。ただし
URL同期・履歴 (pendingHistoryAction) との絡みがあるためテスト工数は方針Aの2〜3倍。

### 推奨

まず**方針A**で見た目と情報密度の問題を解消し、その際に topNSlidersFragment /
オフセット行の共通化だけ先行して行う（方針Bの部分的先取り）。
方針Bのフル抽出は、次にコントロールを追加する需要が出た時点で実施が費用対効果的。
