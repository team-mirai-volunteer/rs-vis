# /quality と /policy-evaluation の統合

## 背景

`/quality`（全事業の支出先データ品質スコア）と `/policy-evaluation`（30事業パイロットの政策評価ダッシュボード）は、
対象データも UI トーンも異なる2ページとして並立していた。

- `/quality`: ライト/ダーク両対応・情報密度重視の実務テーブル。全事業、ヒストグラム絞り込み、
  府省庁・金額レンジフィルタ、ページング、支出先一覧＋計算根拠の詳細ダイアログ。
- `/policy-evaluation`: ダーク固定のプロダクトLP調トーン。データは fixture の30事業のみだが、
  政策評価（AI判定の政策設計明瞭度・証拠準備度）、推奨判断、改善アクション、確度、政策類型、
  AI の判断理由、「暫定」の明示という固有の価値を持っていた。

## 決定

`/quality` をベースに統合し、**指標体系は policy 側に一本化する**。トーンは `/quality` に統一。

| 項目 | 決定 |
|------|------|
| 指標 | 品質スコアの各軸を policy の指標に統合。一覧は政策評価・執行透明性・総合点・推奨・改善アクションの5指標に絞る |
| 政策評価の範囲 | 全事業。有効性軸(E)を成果設計スコアの土台にし、AI精査済の30事業のみ高精度値で上書き |
| 品質軸の生スコア | 一覧から外し、詳細ダイアログ・展開行に集約 |
| ルート | `/quality` に統合。`app/policy-evaluation/` は削除（未コミットの新規ディレクトリだった） |
| ロジック配置 | `app/lib/policy-evaluation.ts` に純ロジックとして切り出し（CLAUDE.md のレイヤ規約） |

### 指標の重複解消

統合前は2系統のスコアが並立していた。実態としては以下が重複していたため、policy 側に寄せて解消した。

| 重複していたもの | 統合後 |
|---|---|
| policy の執行透明性（fixture の baseline 30件・焼き付き値）と 品質軸A/B/C | **執行透明性** = 品質軸A/B/C の加重平均（30/25/30）を実データから全事業分算出 |
| policy の designClarity と 品質軸E（有効性＝成果設計の明確さ・AI判定・全事業） | **政策評価** の成果設計スコアに統合。精査済は designClarity、それ以外は軸E |
| policy の政策総合点 と 品質スコア総合 | 一覧は **総合点** に一本化。品質スコア総合は詳細側へ |

## 評価モデル

```
成果設計スコア = 精査済 ? designClarity × 25 : 成果設計の判定(0-100)
検証可能性     = 精査済 ? evidenceReadiness × 25 : null（未評価）
政策評価   = 加重平均([成果設計 65, 検証可能性 35])
執行透明性 = 加重平均([支出先の明確さ 30, 使途の説明 25, 収支の一致 30])
総合点     = 加重平均([政策評価 40, 執行透明性 20, 検証可能性 30])

不用率     = (予算額 − 執行額) / 予算額   ※総合点には不算入。縮小判断のみに使う
```

加重平均は欠損項目を重みごと除外して再正規化する（`weightedAvailable`）。
全項目欠損なら 0 点ではなく null を返し、「低評価」と「未評価」を区別する。

**精度は2段階**。`basis: 'pilot'` は AI が成果の検証可能性まで精査した事業（一覧に「精査」バッジ）、
`basis: 'derived'` は成果設計の判定からの推定で検証可能性が未評価。

改善アクションでは、他に指摘が無く検証可能性が未評価の場合に「成果検証」へ落とす分岐を末尾に置いている。

## 実装

### 追加

- **`app/lib/policy-evaluation.ts`** — 純ロジック。`buildPolicyEvaluations(qualityItems, pilots)` が
  全事業分の `PolicyEvaluation[]` を返す。判定ルール（`chooseRecommendation` / `chooseImprovementAction`）は
  `evidenceReadiness: number | null` を受けるよう変更し、それ以外の閾値は元の挙動のまま。
- **`app/api/policy-evaluation/route.ts`** — AI精査済事業（`openai/gpt-5.6-luna` のラン × fixture）の
  評価結果のみを返す。全事業分の算出はクライアント側で品質スコアと突き合わせて行う（ペイロード二重化の回避）。
  精査結果はベンチマークの基準年度 2025 でのみ重ね合わせる。

### `/quality` への統合

- **一覧列**: 政策評価 / 執行透明性 / 総合点 / 推奨 / 改善アクション（すべてソート可）。
  品質軸列（総合・特定可能性・使途説明性・収支整合性・有効性・構造）は一覧から撤去。
- **サマリ帯**: 全事業の平均政策評価・平均執行透明性・平均総合点・終了廃止候補数と、
  `AI精査済のみ` / `推奨` / `改善アクション` / `政策類型` フィルタ（各選択肢に件数を表示）。
- **分布ヒストグラム**: 軸に総合点・政策評価・執行透明性を追加し、既定を総合点に変更。品質軸も選択可。
- **詳細ダイアログ**: 政策評価パネル（折りたたみ）。精度バッジ、内訳、AI の判断、推奨理由、暫定注記。
  推定行では「証拠準備度: 未評価」「有効性 N からの換算」と明示。
- **展開行**: 政策評価の要約に加え、一覧から外した品質スコア総合・収支整合性・構造を集約。
- **ヘッダ**: タイトルを「事業別 政策評価・執行透明性スコア」に変更、`/model-lab` へのリンクを追加。

### 変更・削除

- `app/model-lab/page.tsx` の「政策評価へ」リンク先を `/policy-evaluation` → `/quality`。
- `app/policy-evaluation/`（`page.tsx` / `PolicyEvaluationTable.tsx`）を削除。

## スクリーニングの再調整

初版は挙動を変えずに移設したため、全事業スケールで機能しなかった。以下を作り直した。

### 1. 絶対閾値 → 母集団内のパーセンタイル帯

総合点は複数指標の加重平均のため中央に強く圧縮される（実測 p1=42 / p50=72 / p99=89）。
`overallScore <= 35`（終了・廃止候補）や `<= 42`（縮小）は**構造的に到達不能**だった。
帯をパーセンタイル（最下位2% / 下位10% / 下位25% / 下位50%）で定義し、
各帯には絶対条件（成果設計の明確さ等）を併置して、母集団全体が良好な場合に機械的に下位N%が
見直し対象にならないようにしている。

### 2. 「証拠不足 → 廃止候補の対象外」を条件付きに

推定行は証拠準備度が null のため、従来は全事業の99.5%が終了・廃止候補になり得なかった。
成果設計の判定（0-10）は **0 =「記載が空、または寄与が全く読み取れない」＝情報不足**、
**1以上は「活動と便益の紐づきが弱い」等の積極的な低評価**である。
この境界を使い、0（情報なし）は対象外のまま、1以上の積極的な低評価は対象に含めるようにした。
「情報が無いことを見直しシグナルに転化しない」という元の方針は維持している。

### 3. 予算規模の評価をやり直した

旧 `budgetRisk = log10(予算額) / log10(最大予算額)` は**規模の単調変換にすぎず、予算規模の評価ではない**。
しかも総合点の10%を占めており「大きいほど総合点が下がる」という値判断が埋め込まれていた。

縮小の根拠を**不用額（予算と執行の乖離）**に置き換えた。実測で不用額は **20.3兆円＝予算の13.7%** あり、
旧モデルはこれを完全に見落としていた。

- 不用率 = (予算額 − 執行額) / 予算額。閾値は母集団 p75、不用額1億円以上を材料性の下限とする
- **執行実績が無い事業（執行額0・223件）は評価対象外**。災害予備施設・金融危機対応などの
  待機的経費であり、「全額不用」と扱うのは誤りのため
- **不用率は総合点に算入しない**

### 4. 使い切りインセンティブへの対処

不用額を減点にすると、年度末の使い切りを誘発する。返納は本来適切な行動である。そのため:

- 不用は事業評価（総合点）に影響させない。見直し対象は事業ではなく**翌年度の計上額**
- 「消化すれば逃げられる」を塞ぐため、対になる旗を立てる:
  **執行率95%以上 かつ 不透明支出比20%以上**（251件・23.8兆円）は「継続」とせず要改善＋情報開示

### 5. 改善アクションの順序

支出先が特定できない状態では成果検証も設計議論も成立しないため、情報開示・ガバナンスを
成果検証・KPI改善より前に移した。またガバナンス改善は精査済事業のタグにしか反応せず
構造的に0件だったので、再委託深度3以上・孤立ブロック有りを全事業共通の条件として追加した。

## ラベルの平易化

`軸A/B/C/D/E` という内部の分類記号は利用者に伝わらないため、画面上から撤去した。

| 内部名 | 画面表示 |
|---|---|
| 軸A 特定可能性 | 支出先の明確さ |
| 軸B 使途説明性 | 使途の説明 |
| 軸C 収支整合性 | 収支の一致 |
| 軸E 有効性 | 成果設計の明確さ（政策評価の内訳としてのみ） |
| 軸D 構造 | ブロック構造の整合（参考） |

また**有効性(E)は政策評価に吸収されている**（推定行では `政策評価 = 軸E` と完全一致、
精査済では designClarity に置き換わり未使用）ため、独立した指標としての掲示をやめた。
分布の軸の選択肢からも外し、詳細ダイアログでも重複表示しない。

## 画面構成

指標の定義はツールチップではなく、ヘッダーの統計と「指標の読み方」に集約した。

- **ヘッダー**: 事業数と、政策評価／執行透明性／総合点それぞれの平均・中央値・レンジ、終了廃止候補件数。
  各指標が実際どの辺りに分布しているかがページを開いた時点で分かるため、列ヘッダのツールチップは撤去した。
- **絞り込み**: 推奨・改善アクション・政策類型をすべて件数付きボタンに統一（推奨は判断色で着色）。
  ヒストグラム脇は「表示 / 全件」の連動表示にした（旧「全件」ボタンは固定値を出すだけで意味が無かった）。
- **AI精査／推定の区別は画面から撤去**。いずれ全事業を精査する前提のため、
  一時的な状態を UI の恒久要素にしない。内部の `basis` は残しているが、
  利用者に見えるのは「成果の検証可能性: 未評価」という事実のみ。

### 一覧テーブルの安定化

ソートするたびに列幅が変わって UI がずれていた（`table-auto` が中身に応じて幅を再計算するため）。
`table-fixed` + `colgroup` の固定幅に変更し、溢れるセルは省略記号＋`title` 属性でフォローする。
ソートを5回切り替えても列幅が1pxも動かないことを Playwright で確認済み。

スコアの横に出していたバーは、数値と情報が重複するうえ幅を食うため廃止した（数値のみ）。

列順は判断の粒度が粗い順に **総合点 → 政策評価 → 執行透明性 → 推奨 → 改善アクション**。
まず総合点で当たりをつけ、内訳へ降りる並びにしている。

絞り込みは上から「金額の下限上限 → 指標の足きり（総合点・政策評価・執行透明性）→ 推奨・改善・類型のドロップダウン」の順。
同じ数値入力どうしを隣接させ、ドロップダウンが数値入力に挟まれないようにしている。
順位帯ベースの推奨とは別に、「政策評価50以下だけ見る」といった絶対値での切り出しができる。

### 品質スコアの撤去と詳細表示の統一

品質スコア総合（旧の合成値）は、分解後の指標と重複していた。

```
品質スコア総合 = 支出先の明確さ28 + 使途の説明22 + 収支の一致15 + 成果設計35
                 └────── 執行透明性の構成要素 ──────┘   └ 政策評価の材料 ┘
```

つまり執行透明性と政策評価を混ぜ戻したものであり、両方と並べると何が何の内訳か分からなくなる。
画面から完全に撤去した（分布の軸・モーダル・展開行・一覧すべて）。

さらに計算根拠のアコーディオンは旧の重み（28/22/15/35）を説明したままで、
実際に表示している総合点の算出とも一致していなかった。実式に書き換えたうえで、
モーダルと展開行の構成を揃えた。

| 区画 | 内容 |
|---|---|
| 政策評価 | 成果設計の明確さ×65 + 成果の検証可能性×35 |
| 執行透明性 | 支出先の明確さ×30 + 使途の説明×25 + 収支の一致×30 |
| 総合点 | 政策評価×40 + 執行透明性×20 + 検証可能性×30 ＋ 母集団内の順位 |
| 予算と執行 | 執行率・不用額（総合点に不算入・縮小判定のみ） |
| 参考 | ブロック構造（スコアに不算入） |

展開行も同じ5区画（政策評価／執行透明性／予算と執行／推奨と改善／組織・支出構造）に統一した。

## ルーブリック方式のA/B比較（実施済み・スクリプトは削除）

全件へ広げる前に、軸Eの弁別力を上げる方式を30事業ベンチマークで比較した。
比較用スクリプト（`scripts/quality-rubric-variants.ts` / `scripts/benchmark-openrouter-models.ts`）は
本番パイプラインに `--benchmark` を実装した時点で二重管理になるため削除した。以下は実測の記録。

モデルはすべて `openai/gpt-5.6-luna`、対象は同一の30事業。

| 方式 | 使用段階 | 同点率 | 正規化σ | エントロピー | 3段階集中 |
|---|---|---|---|---|---|
| comparative（N件同時ランキング） | 11/11 | 0.0% | 0.299 | 0.994 | 30.0% |
| anchored（アンカー事例との距離） | 8/11 | 17.7% | 0.164 | 0.729 | 73.3% |
| substance（実質重視プロンプト） | 5/11 | 19.3% | 0.124 | 0.649 | 73.3% |
| production（当時の現行） | 5/11 | 24.6% | 0.108 | 0.599 | 80.0% |

**comparative の数値はそのまま信じてはいけない。** N件をランキングさせれば相異値N・同点0は構造的に出る。
判断材料は他モデルとの順位相関の方で、comparative は deepseek と ρ=0.786、glm 0.672、haiku 0.634 と
広く散らしつつ合議と一致していた。ただしバッチ内順位しか出ないため、5,794件を一度にランクできない以上
バッチ跨ぎの比較可能性が担保できず、本番採用は見送った。

**substance は全方式と ρ≈0.01〜0.29 で無相関**、散らばりも小さく、採用しなかった。

**anchored を採用**。glm ρ=0.718・deepseek ρ=0.749 と一致度が高く、弁別力も素直に改善した。
その後さらに「段階採点」（軸ごとに全事業を横断して採点）を加え、設計8/11・検証7/11・費用対内容9/11 まで改善している。
段階化はバッチ内比較を働かせるため、comparative の利点を absolute scale のまま取り込む狙い。

## 今後の方向

有効性(E)は暫定の土台にすぎない。最終的には**政策評価・証拠・予算規模査定を Luna に評価させる**方針で、
その時点で軸Eからの推定経路（`basis: 'derived'`）は不要になる。
`buildPolicyEvaluations` は精査結果があればそちらを優先する構造なので、
Luna の評価が全事業に行き渡れば入力を差し替えるだけで移行できる。
予算規模査定も現状は不用率・執行率という機械計算だが、同様に Luna の査定へ寄せる余地がある。

**政策類型の粒度**も同じ話に乗る。現在の6類型はベンチマーク fixture 由来で、
付与されているのは30事業のみ・粒度も粗い。細分化するには全事業の分類が必要で、これは Luna の評価パスと同時に行うのが自然。
UI 側はチップからドロップダウンへ戻してあるので、項目数が増えてもそのまま収まる。

## 残っている論点

- **他事業と統合が2件のみ**。統合シグナル（目的が広い・複数施策の束ね）は精査済事業のタグにしか
  無いため、全事業では実質機能していない。全事業共通の代理指標が要る。
- **政策評価の粒度**。推定行では成果設計の判定（0-10の11段階）がそのまま政策評価になるため、
  実質11段階しか値を取らない。順位帯で切っているので弁別は効くが、同点が多い。
- 閾値（帯の%・不用率p75・不透明比20%）は今回の母集団から決めたもので、年度が変われば再確認が要る。
