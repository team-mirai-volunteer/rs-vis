## 1. `/subcontracts` の29MB全量ダウンロード（最優先）

`app/subcontracts/page.tsx:170`

```ts
fetch(`/data/subcontracts-${year}.json`, { signal: controller.signal })
  .then(r => r.json())
  .then(data => setGraphs(Object.values(data)))
```

実測: 生 **29MB** / gzip後でも **4.47MB**。これを一覧（ページング付きテーブル）を描くためだけに全部取得している。
一覧が必要なのは `projectId / name / ministry / 合計金額 / 再委託有無` 程度で、ブロック明細・支出先配列は詳細ページ（`/api/subcontracts/[projectId]`）側にある。

**提案**: `scripts/generate-subcontracts.ts` から一覧専用の軽量インデックス（`subcontracts-index-{YEAR}.json`、数百KB想定）を副産物として出力し、一覧ページはそちらを読む。詳細は既存APIのまま。
効果: 初期表示のダウンロード量 4.47MB → 100KB前後、JSONパースによるメインスレッド長時間ブロックも解消。

同じ構図が `/sankey-svg`（`/data/sankey-svg-{year}-graph.json` 生13.5MB / gzip 1.4MB, `page.tsx:1172`）にもあるが、こちらは図の描画に全ノードが要るため妥当。ただし後述16のキャッシュ設定は効かせるべき。

## 2. `/api/quality-scores` のレスポンス肥大

- 2025年度の実測は **5,794件・約6.4MB転送**。`Content-Encoding` なし（＝無圧縮）、`Cache-Control` ヘッダ **なし**（他の全APIは `API_CACHE_CONTROL` を付与しているのにこのルートだけ欠落）。
- 約45フィールドを常に全件返し、`/quality` 側でフィルタ・ソートしている。

**提案**:
- `Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800`（既存の `API_CACHE_CONTROL`）を付ける ← 1行で効果大。
- 一覧表示に不要な `effectiveReason`（自由記述）等をデフォルトで落とし、`?fields=` か詳細取得APIに分離する。
- 中期的にはサーバ側ページング（`/api/search/projects` は既に `limit/offset` を実装済みなので流用可）。

## 3. サーバ側インメモリキャッシュのメモリ圧

各ルート／ローダがモジュールスコープの `Map` に**年度別・全量**を保持し、解放しない。

| データ | 生サイズ | キャッシュ箇所 |
|---|---|---|
| `recipient-index-{2024,2025}` | 31MB × 2 | `app/lib/api/recipient-index-loader.ts`（＋ alias→key の派生Mapも別途構築） |
| `subcontracts-{year}` | 29MB | `app/api/subcontracts/[projectId]/route.ts` |
| `rs{year}-project-details` | 13MB × 2 | `app/api/project-details/[projectId]/route.ts` |
| `project-quality-scores-{year}` | 5.6MB | **2箇所で二重に**（後述6） |

JSONはパース後のJSオブジェクトで生テキストの2〜4倍のヒープを食う。全部が同一インスタンスに載ると容易に1GB級になり、Vercelの関数メモリ上限に触れる（アクセスパターン次第で断続的な500になる）。

**提案**: 少なくとも「巨大かつピンポイント参照」のもの（`recipient-index`、`subcontracts`、`project-details`）は
- 生成時にキー分割（`public/data/subcontracts/{pid}.json` 等）して静的配信に寄せる、または
- 事前に「キー→バイトオフセット」の索引を作って `fs` の部分読み出しにする、
のどちらかでフルロードを止める。手軽な緩和策としてLRU上限＋TTLの導入でもよい。

## 4. モバイル表示の再設計

390×844pxの実表示で以下を確認した。

- `/sankey-svg`: 事業列・支出先列の大部分が画面外になり、全体の流れを把握しにくい。
- `/quality`: ドキュメント幅が約870pxまで広がり、ページ全体に横スクロールが発生する。表は実質的にPIDと事業名しか見えない。
- `/mof-budget-overview`: モバイル時も図の内部幅を1200pxに固定しており、横スクロールが前提。タイトルも固定ボタンと競合しやすい。
- `/subcontracts`: テーブル内スクロールは可能だが、右側に重要指標が存在することが分かりにくい。

デスクトップ版を単純縮小するのではなく、モバイルでは情報を段階的に開示する。

- サンキー: 「省庁 → 事業 → 支出先」のドリルダウン一覧を基本表示にし、図は任意で開く。
- 品質: 事業名・府省庁・総合点・主要な警告だけをカード表示し、詳細指標は展開する。
- 再委託: PID・事業名・支出額・再委託階層・構造を優先列とし、残りは詳細へ移す。
- MOF: 予算総額・RS対象比率・一般／特別会計の構成をカードまたは棒グラフで先に示す。

**受け入れ条件**

- 390px幅でドキュメント全体の横スクロールが発生しない。
- 主要な検索、年度切替、詳細表示を片手で操作できる。
- 初期画面だけでページの目的と主要な数値を理解できる。

## 5. トップページと共通ナビゲーション

現在の `/` は `/sankey-svg` へ即時リダイレクトするため、「トップへ戻る」が機能選択ではなくサンキー図への移動になっている。`/quality` と `/mof-budget-overview` への導線も発見しにくい。

トップページに以下の4つの入口を設ける。

- 予算の流れを見る
- 支出先・事業を検索する
- 再委託構造を調べる
- データ品質を比較する

各ページには共通のアプリ切替メニューを置く。年度切替はページ間で可能な限り維持する。

**受け入れ条件**

- 公開4ページすべてへトップページから1クリックで到達できる。
- 各カードに「この画面で分かること」を1文で示す。
- 現在位置がナビゲーション上で識別できる。

## 6. `quality-scores` ローダの重複と型の乖離

- `app/lib/api/quality-scores-loader.ts`（`/api/search/projects` が使用）
- `app/api/quality-scores/route.ts` 内の `loadData()`（同ファイルに `QualityScoreItem` を再定義）

同じファイルを読み、同じ集計（平均・中央値・標準偏差・最頻値）を**コピペで二重実装**し、**別々にキャッシュ**している。さらに型が乖離していて、AI再設計で追加された新軸（`axisIdentify` / `axisPurpose` / `axisEffective` / `aiSource` 等）は route 側にしか無い。`.gz` フォールバックも route 側だけ。

CLAUDE.md のレイヤ規約「API Layer はロジックを `app/lib/` に委譲」にも反する。

**提案**: `app/lib/api/quality-scores-loader.ts` に一本化し、型は `types/` へ移す。route は薄いHTTPハンドラにする。副次的にメモリも半減。

## 7. テストが実質機能していない

- `tests/e2e/sankey-svg.spec.ts`（408行）は `page.goto('/sankey-svg')` と**相対パス**を使うが、**`playwright.config.ts` がリポジトリに存在しない**（git管理外）。したがって `npm run test:e2e` はそのままでは動かない（baseURL未設定）。
- ユニットテストは**0件**。テストランナー（vitest/jest）自体が未導入。

`app/lib/` は「Pure Sankey生成、HTTP・React禁止」と規約で定義された純粋関数群で、`sankey-svg-filter.ts`（949行）・`mof-sankey-generator.ts`（989行）・`subcontract-layout.ts`（440行）と、テストの費用対効果が最も高い層がまるごと無防備。

**提案**: `playwright.config.ts`（`baseURL` + `webServer`）をコミットし、vitest を入れて最低限
- `filterTopN` / `computeLayout` の件数・合算の不変条件
- 「その他」と「その他の支出先」の取り違え検知
- CLAUDE.md の Known Bugs にある「同一支出先が複数ブロックに出現するときの合算」
をテストで固定する。既知バグが仕様書にしか無い状態は再発する。

## 8. CI が無い

`.github/` にはテンプレート類のみで **workflows が無い**。`tsc --noEmit` / `next lint` / e2e がPRで自動実行されない。

**提案**: PR時に `npx tsc --noEmit` + `npm run lint` + （7の整備後）e2e を走らせるワークフローを追加。現状 tsc はクリーン、lintは警告のみなので今すぐ導入しても赤くならない。

## 9. メタデータ／SEO

- `metadata` の定義は `app/layout.tsx` の**1箇所のみ**。全ページが「行政事業レビュー サンキー図 - 予算・支出可視化」という同じ title / description になる（`/subcontracts` も `/quality` も同一）。
- `openGraph` / `twitter` / OGP画像の指定なし → SNS共有時に何も出ない。
- 全ページが `'use client'` のため初期HTMLが空。特に `/subcontracts/[projectId]`（5,003ページ）はクロール・共有価値が高いのにメタ情報ゼロ。

**提案**: 各ルートに `layout.tsx` を足して静的 `metadata` を付与。`/subcontracts/[projectId]` は `generateMetadata()` で事業名をtitleに入れる（データは既にサーバ側にあるので容易）。

## 10. サンキー図の初心者向けプリセット

Top N、ズーム、関連ノード表示、正規表現検索など分析機能は充実している一方、初見ユーザーが最初に何を操作すべきか判断しにくい。

以下のプリセットを用意し、内部的には既存のURL状態へ展開する。

- 全体をざっくり見る
- 最大支出先10件
- 特定省庁を深掘り
- 再委託の多い事業
- データ品質の低い高額事業

初回ガイドでは「線幅＝金額」「Top N以外は集約される」「その他とその他の支出先は別概念」を説明する。

## 11. 年度比較モード

現状の年度切替は単年度表示で、差分を利用者が記憶して比較する必要がある。比較モードとして次を表示する。

- 予算額・執行額の前年差と増減率
- 新規／終了事業
- 支出先の新規参入／退出
- 品質スコアの改善／悪化ランキング
- 府省庁別の増減

比較条件をURLへ保存し、同じ表示を共有・再現できるようにする。事業IDの年度間対応が保証されない場合は、IDだけでなく名称・担当組織による対応付けルールを明文化する。

## 12. アクセシビリティ

- サンキー図のSVGノードへフォーカスを当て、Enter／Spaceで選択できるようにする。
- 図と同等の情報へ到達できる表形式の代替表示を用意する。
- 品質一覧のクリック可能な行をキーボード操作可能にするか、明示的な詳細ボタンへ統一する。

## 13. `app/sankey-svg/page.tsx` の肥大化

4,696行 / `useState` 86個 / `useEffect` 37個 / インラインstyle 259箇所の単一クライアントコンポーネント。URL状態のシリアライズ（`SankeyUrlState` 44フィールド）、ズーム・パン、検索、フィルタ、サイドパネル、ミニマップ、フォント制御が全部同居している。

既に `client/components/SankeySvg/*` への切り出しが始まっているので、その延長で
- URL状態 ↔ ステートの同期を `useSankeyUrlState()` に
- ズーム/パン/タッチを `useSankeyViewport()` に
- サイドパネル・ツールチップをコンポーネントへ
と段階的に分割するのが妥当。**7のテスト整備を先に**やらないと安全に切り出せない点に注意。

## 14. lint警告16件

- 未使用コード7件（`createAccountDetailNodes`、`graphDataStats`、`totalWindowSpending` 等）→ 削除でよい。
- `react-hooks/exhaustive-deps` 7件（`app/sankey-svg/page.tsx` 5件、`app/quality/page.tsx` 2件）→ **stale closure による「特定の操作順序でだけ更新されない」系バグの温床**。`budgetNodeByPid` が2箇所の `useMemo` から抜けているのは要確認。

## 15. スタイル方針の不一致

Tailwind（v3）を導入・ビルドしているが、`className` を使っているのは6ファイルのみで、実装の大半はインラインstyleオブジェクト。色（`#2563eb` 等）もハードコードが散在。どちらかに寄せるか、少なくとも色・フォントサイズをトークン化したい。

## 16. 静的データのキャッシュヘッダ

`/data/*.json` は Next 標準の `Cache-Control: public, max-age=0`。ETag による304は効くが、13.5MBのファイルに対して毎回リクエストが飛ぶ。
データはデプロイ時にしか変わらないので、ファイル名にビルドハッシュを付けて `immutable` を返すか、`next.config.ts` の `headers()` で `s-maxage` を設定するのが望ましい（APIには既に同等の方針が入っているのに静的側だけ抜けている）。

## 17. 開発初期セットアップ

今回の起動で判明: `npm install` 後に `npm run dev` しても **`public/data/*.json` が無いため主要ページが動かない**（`.gz` の展開は `prebuild` フック＝`npm run build` 時にしか走らない）。`/api/quality-scores` と `/api/project-details` にはその場で `.gz` を展開するフォールバックがあるが、`/subcontracts` と `/sankey-svg` が読む静的JSONには無い。

**提案**: `"dev": "npm run predev && next dev --turbopack"` 相当（もしくは `predev` フック）で `scripts/decompress-data.sh` を走らせる。1行で開発体験が揃う。README への追記でも可。
