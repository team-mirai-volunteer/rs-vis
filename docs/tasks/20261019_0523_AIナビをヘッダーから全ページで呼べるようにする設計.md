# AI ナビをヘッダーから全ページで呼べるようにする（設計）

## 依頼

サンキー図（/budget-sankey）にある AI ナビ（AI に聞いて絞り込む）を、サンキー図だけでなく色々なページで使いたい。ハンバーガーメニューのボタンの左に置いて、どこからでも AI を呼べるようにする。

## 現状

| 部品 | 場所 | 役割 |
|---|---|---|
| `AiFilterChat` | `client/components/unified-budget/AiFilterChat.tsx` | 会話 UI（BYOK 設定・ログ・入力）。サンキー図の検索ピルの直下に開く。結果 `SankeyChatResult` を `onApply` で親へ渡す |
| `runSankeyChatAgent` / `chat-core.ts` | `app/lib/ai/` | LLM のツール呼び出しループ。ツールは事業検索・支出先検索・事業詳細・AI 評価・再委託チェーン・年度比較・ハイライトと、条件確定の `submit_result`。結果が無いときはテキスト回答（聞き返し・解説） |
| `/api/ai/sankey-chat` | `app/api/ai/sankey-chat/route.ts` | サーバー側 LLM 経路（BYOK が無いとき）。GET で有効判定 |
| `applySankeyQueryToUnifiedFilter` | `client/lib/unified-ai-filter.ts` | 結果のクエリをサンキー図のフィルターへ写す |
| `serializeFilter` / `parseFilter` | `app/budget-sankey/page.tsx`（非公開） | サンキー図のフィルター ⇄ URL |
| `chat-history-store.ts` | `client/lib/ai/` | 会話履歴の IndexedDB 永続化（旧 AiChatPanel 用に作成済み。複数セッション） |
| `HeaderFrame` | `components/navigation/AppHeader.tsx` | 全ページ共通のヘッダー。`AppHeaderProvider` 経由で root layout に 1 つだけ描かれる |

ポイント: エージェントはすでに「サンキー図の絞り込み」以上のことができる（事業詳細・評価・再委託の説明、年度比較）。サンキー図専用なのは **入口（検索ピルの AI ボタン）と出口（フィルターへの適用）** だけ。

## 提案

### 1. 入口をヘッダーに移す

- `HeaderFrame` のハンバーガー（`PageNavMenu`）の左に AI ボタン（Sparkles アイコン＋「AI」、`variant="outline" size="icon"` でメニューと同じ見た目）を置く。
- 押すと `AiAssistant`（`AiFilterChat` を改名・移設）が **ヘッダー直下の右寄せの浮いたカード**（sm 以上は幅 440px、sm 未満は画面幅いっぱいのボトムシート）として開く。
- `AiAssistant` は `AppHeaderProvider`（root layout）に 1 つだけ置く。**ページを移動しても会話が消えない**（従来はサンキー図を離れると消えていた）。履歴は `chat-history-store` に保存して再訪時に続きから。
- サーバー AI が無効で BYOK も未設定の環境では、ボタンは出すが押すとキー設定の案内（今の挙動と同じ）。サイト提供 AI の有効判定（GET）は今どおり。

### 2. 出口を「ページが受け取れれば適用、無ければリンクで案内」にする

結果 `SankeyChatResult`（正規化済みクエリ＋要約）の扱いを、ページごとの登録制にする。

```ts
// client/lib/ai/result-handler.ts（新規）
// ページが useAiResultHandler(handler) で登録。登録が無いページでは null
const handler = useAiResultHandler(result => { setFilter(...); setFilterOpen(false); });   // /budget-sankey
```

- `/budget-sankey`: 今どおりフィルターへ即時適用（登録ハンドラ）。
- 登録が無いページ（評価一覧・バブル・委託構造・基金など）: 結果カードに **「サンキー図で見る」**（クエリ → `serializeFilter` で URL。`serializeFilter` を `app/lib/unified-budget/filter-url.ts` へ移して export）と、要約に含まれる事業（上位 N 件）への **各ページの詳細リンク**（評価一覧 `?detail=pid`、委託構造 `/subcontracts/pid`）を出す。
- 会話の文脈に `page`（現在のページ名）を加え、システムプロンプトに「ユーザーは今 ○○ ページを見ている。そのページで見られる情報を優先して案内する」を 1 行足す。ツールは変えない。

### 3. 段階

| 段階 | 内容 | 規模 |
|---|---|---|
| A | 入口のヘッダー移設・会話の永続化・サンキー図での即時適用・他ページでは「サンキー図で見る」リンク | 中（UI 移設＋ URL 化＋ハンドラ登録） |
| B | 評価一覧・委託構造への直接適用（評価一覧は `?pid=` の一覧フィルター、委託構造は `fm`/`fnp`/`bmin` などの既存 URL パラメータに写す） | 小〜中（ページごとのアダプタ） |
| C | バブルチャートでのハイライト、基金・租税特別措置ページ向けのツール追加 | 大（エージェントのツール拡張） |

まず A を実装し、B はページごとに足す。

### 決めてほしいこと

1. **段階 A から始めてよいか**（他ページでは「サンキー図で見る」リンク＋事業への詳細リンク。即時適用はサンキー図だけ）。
2. ボタンの文言: 「AI」のみか、「AIに聞く」か。ヘッダーの右スロットが混む sm 未満ではアイコンだけにする。
3. サンキー図の検索ピル内の「AI」ボタンは残すか（ヘッダーと二重になる。残すなら同じパネルを開く）。削除を推奨。

## 触るファイル（段階 A）

- `components/navigation/AppHeader.tsx`: AI ボタンと `AiAssistant` のマウント、開閉状態
- `client/components/ai/AiAssistant.tsx`（`AiFilterChat.tsx` から移設・改名）: 位置の自前決定、結果カードのリンク化、履歴の永続化
- `client/lib/ai/result-handler.ts`（新規）: ページ登録制のハンドラ（Context）
- `app/lib/unified-budget/filter-url.ts`（新規）: `serializeFilter`/`parseFilter` を `app/budget-sankey/page.tsx` から移動
- `app/budget-sankey/page.tsx`: 検索ピルの AI ボタンと `searchPopover` を外し、`useAiResultHandler` で適用を登録
- `app/lib/ai/chat-core.ts`・`types/sankey-ai-chat.ts`: `context.page` の追加（任意）

## 将来像: サイト全体の情報を MCP とスキルで取れるようにする

依頼者の長期の狙いは、このサイトの情報を外部の AI（Claude Code・claude.ai・他のエージェント）から MCP とスキルで取得できるようにすること。ヘッダーの AI ナビはその「サイト内の 1 利用者」と位置づける。

### 今の構造がそのまま土台になる

`app/lib/ai/chat-core.ts` は、ツール定義（`TOOLS`: OpenAI 互換の function 定義）と実行の抽象（`ChatToolExecutor`）を分けた Pure 層で、実行の実体は 2 つある（サーバー `tool-executor-server.ts` = ローダ直呼び、ブラウザ `client-tool-executor.ts` = 公開 API fetch）。MCP のツールは「名前・説明・JSON Schema・実行関数」なので、**同じ `TOOLS` と `ChatToolExecutor` を 3 つ目の呼び出し元（MCP サーバー）から使う**だけでよい。

```
            ┌─ サイト内 AI ナビ（ヘッダー）    … LLM が TOOLS を function calling で呼ぶ
TOOLS +     ├─ /api/mcp（MCP サーバー）        … 外部の AI が MCP で同じツールを呼ぶ
Executor ───┤
            └─ 公開 REST（/api/*）              … 人・スクリプトが直接叩く（docs/api-guide.md）
```

### 進め方（AI ナビの段階 A・B と並行できる）

1. **ツールカタログを 1 か所に**: `TOOLS` を「サンキー図の絞り込み用」から「サイトの情報を引く用」へ名前と説明を整理する（`run_sankey_query` → `search_projects_by_conditions` など。既存名は別名で残す）。ページが増えるたびにここへツールを足す（基金・概算要求・租税特別措置・事業者・財政余力の試算）。段階 C はこの作業そのもの。
2. **MCP サーバー**: Next.js の Route Handler で `@modelcontextprotocol/sdk` の Streamable HTTP を `app/api/mcp/route.ts` に置く。ツールは `TOOLS` から機械的に登録し、実行は `tool-executor-server.ts` に委ねる。認証は当面なし（公開データ）。レートリミットは公開 REST と同じ方針。LLM は呼ばないので従量課金の心配がなく、Vercel でも常時有効にできる。
3. **スキル**: `skills/rs-vis/SKILL.md`（公開リポジトリに置く）に、ツールの使い分け、データの約束事（金額は 1 円単位、「その他」と「その他の支出先」の違い、RS シート年度 = 予算年度 + 1、AI 評価は試行で公式評価でない、出典の表示義務）、典型的な問い（「○○省で 1 者応札が続く事業」など）の手順を書く。Claude Code からは `npx skills add` 相当で取り込める形にする。
4. **ドキュメント化**: `docs/api-guide.md` に MCP の接続方法を足し、トップページの「データについて」からリンクする。

### AI ナビの設計への影響

- 段階 A の「入口と出口をツール層から切り離す」方針は、そのまま MCP 化の前提になる（入口がヘッダーでも MCP でも、ツール層は同じ）。
- 「ページで見る」リンク（結果 → 各ページの URL）は MCP でも有用（外部 AI が回答に「このサイトのこの画面で確認できます」と URL を添えられる）。URL 化の関数は `app/lib/` に置き、両方から使う。
- 段階 A のうちに `context.page` を足すときは、MCP 側には無い情報なのでシステムプロンプトの任意項目に留める。

## 実装（2026-10-19）: MCP サーバーの骨組み

AI ナビの段階 A より先に、MCP サーバーを動く状態にした（楽な方から）。

| ファイル | 内容 |
|---|---|
| `app/lib/ai/chat-core.ts` | エージェントループ内の switch を `executeToolCall(name, args, executor, year)` として切り出し（引数検証込み）。`submit_result` はループ固有なので残し、`DATA_TOOL_NAMES`（公開できるツール名）を export |
| `app/lib/ai/mcp-tools.ts`（新規） | MCP 向けカタログ。`TOOLS` から `submit_result` を除き、各ツールの JSON Schema に `year`（"2024"/"2025"）を追加。`MCP_INSTRUCTIONS`（データの約束事）と `resolveToolYear` |
| `app/api/mcp/route.ts`（新規） | `mcp-handler` の `createMcpHandler` に `registerTool` で登録。JSON Schema は `@modelcontextprotocol/server` の `fromJsonSchema` でそのまま渡す（zod への書き換え不要）。実行は `serverToolExecutor`。GET/POST/DELETE を export |
| `tests/mcp-tools.test.ts`（新規） | カタログの形、instructions の必須項目、year の解決、`executeToolCall` の検証と委譲先（スタブ）|
| `docs/api-guide.md` | 「MCP サーバー」の節（ツール一覧・接続・curl の確認手順）|
| `package.json` | `mcp-handler@2.3.0`、`@modelcontextprotocol/server@2.3.1` を追加 |

確認: dev サーバーに対して initialize → tools/list（10 ツール）→ tools/call（search_projects「子育て」= 公開 API と同じ 11 件、get_project_detail、run_sankey_query）が通る。不正な year や metric は SDK の JSON Schema 検証で `isError` になる。

注意: curl から日本語を含む本文を `-d '...'` で送ると Git Bash の文字コードで化けて 0 件になる。UTF-8 ファイルから `--data-binary @file` で送る（api-guide に記載）。
